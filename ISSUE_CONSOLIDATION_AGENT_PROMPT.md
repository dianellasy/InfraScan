# Implement live inference-to-issue consolidation

Implement this feature in the **current InfraScan working tree**: a user submits a JPEG or A119 Mini 2 MP4, the existing asynchronous inference job produces detections, those detections create or update canonical Issues, and the Issues appear in the existing map, detail, and review views. Complete the code and tests, not just a proposal. Preserve all pre-existing working-tree changes, including the uncommitted video/R2 work; do not reset them. Inspect the current code before editing because the ingestion path has changed recently.

## Current integration points

- `frontend/InfraScan frontend/src/App.tsx` already submits JPEGs and MP4s, polls `/api/v1/jobs/{job_id}`, and shows job detections. JPEGs provide `captured_at`, latitude, and longitude. MP4s provide only `camera_utc_offset_minutes`; the API validates embedded A119 GPS and derives the job's initial time and position. Keep these contracts and the current validation behavior.
- `backend/app/services/inference_jobs.py` stores submitted media in R2 and creates the pending job; `backend/inference/celery/tasks.py` invokes `InferenceJobProcessor`. `backend/app/services/inference_processing.py` handles both image and video jobs. The video path samples at most 60 real frames, projects detections using per-frame GPS/heading, and uploads one annotated evidence JPEG per sampled frame. Some accepted frames can still have unlocated detections.
- The precise missing link is `InferenceJobProcessor._save_results`: it writes `EvidenceMedia` and `DetectionRecord` rows and marks the job completed, but never creates/updates an `Issue` or fills `DetectionRecord.issue_id`. `DetectionRecordRepository.add_many` returns the persisted records, so use the existing save transaction as the integration point rather than adding a second independent pipeline.
- `backend/app/models/issue.py` defines Issue, status and review reasons, and `MODEL_CLASS_ISSUE_TYPES` (raw class IDs 0–3 to canonical types). `backend/app/repositories/issues.py`, `backend/app/services/issues.py`, and `/api/v1/issues/map`, `/api/v1/issues/{id}`, `/api/v1/issues/{id}/detections`, `/api/v1/issues/review-queue`, and `/api/v1/evidence/{id}` already provide the read path. The map uses GeoJSON `[longitude, latitude]`; unlocated Issues belong in the review queue. The Stanton–Anaheim seed only inserts demonstration rows.
- Existing integration tests live in `backend/tests/test_inference_workflow.py`, `test_video_workflow.py`, and `test_issue_map.py`. The video workflow test already exercises HTTP submission → R2 fake → Celery task → database → API. Frontend tests include `src/App.test.tsx` and the issue-map tests. Update tests that currently assert `issue_id is None`.

## Required implementation

1. **Create/link Issues for real jobs.** During the worker's existing result transaction, assign every supported-class detection from either an image or a video frame to exactly one Issue. Create a new Issue if no safe match exists; otherwise link to and update the existing one. Keep raw class ID, confidence, severity, bounding box, projected location, frame timestamp, job ID, and evidence ID unchanged. Jobs with zero detections create zero Issues. Do not mark a job completed unless its detections and Issue links commit together. Preserve the existing evidence-object cleanup on failure.
2. **Implement a documented matching rule.** Use a bounded geographic candidate query and actual distance in meters, not degree subtraction or a whole-job grouping shortcut. Match only compatible canonical types and only within a conservative, configurable radius that reflects the current prototype geolocation accuracy. Prefer the closest qualifying Issue with deterministic tie-breaking. Prevent distinct boxes in the same image/frame from collapsing solely because their projected points are close. Support repeated observations of one defect across video frames and separate jobs. Define behavior for nearby conflicting types, low confidence, and previously reviewed/resolved/dismissed Issues without silently changing manual decisions. Keep the rule simple enough to explain and test; document the default radius and its limits.
3. **Use observation times and sound Issue fields.** For an image, use the job's `captured_at` as the observation time. For video, derive each frame's UTC observation time from the GPS-aligned video timeline rather than using the worker processing clock for all frames. Keep `first_seen_at <= last_seen_at`, severity, location/accuracy, status, and review reason consistent as detections accrue. Preserve `DetectionRecord.detected_at` as the inference timestamp if that is its existing meaning. Do not infer precise accuracy the code cannot support.
4. **Handle missing locations and class mapping safely.** A detection whose box cannot be projected must still be saved. Create/link it to an unlocated Issue requiring review using a rule that does not merge unrelated submissions merely because both lack coordinates. Such Issues must be returned by the review queue and excluded from the map. Preserve the current API rejection of an MP4 with no usable embedded GPS track. Define explicit behavior for an unmapped model class; do not invent an IssueType or lose the detection silently.
5. **Make concurrent processing and retries safe.** Two jobs for the same defect should not race into duplicate Issues. Use a PostgreSQL-safe transaction/locking strategy around matching and insertion, without holding database locks while downloading media, decoding video, running the model, or uploading to R2. Duplicate delivery of an already completed job must not add detections or alter counts. Keep candidate search efficient with suitable indexes/migrations if needed.
6. **Finish the user path.** Once a job completes, its detection response should expose the linked `issue_id`; the upload page should offer an obvious route to the corresponding Issue(s) and map. Navigating to the map after completion must fetch the latest Issues; provide a refresh mechanism if needed for a map already open. Reuse the existing map and Issue APIs rather than rendering a second source of truth. Show that an uploaded, located detection appears as a marker within the right viewport and that its detail view shows the supporting detection and evidence.
7. **Address historical unlinked detections.** Inspect existing real rows with `issue_id IS NULL` and provide an idempotent backfill path where the persisted data is sufficient to apply the same matching policy. Keep historical records without enough location/class information reviewable or explicitly report why they cannot be backfilled. Do not use the synthetic map seed as a substitute.
